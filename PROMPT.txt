木材加工厂的干燥车间有六座窑，干燥基准现在是贴在墙上的纸：按树种给一张阶段表，厚板再手写改几格，某座窑的风机偏弱又在旁边加注。操作工每两小时去读一次干湿球温度、称一次样板，自己判断该不该进下一阶段。去年换了一版橡木基准，结果有两座窑还在按旧表走，一批料开裂。厂里想做一个网页系统，把基准的配置、发布和窑的运行过程管起来，页面给工艺员编辑基准、给班长看每座窑走到哪一步。

基准分三层：树种基础表、厚度等级覆盖、单座窑覆盖。每张阶段表是若干行，每行以“含水率降到多少以下”作为进入条件，给出该阶段的干球温度和湿球温度（或干湿球温差）。下层只写与上层不同的格子，未写的继承上层；合并后的有效基准必须是确定的，同一组三层配置无论以什么顺序保存，合并结果都一样。基准以版本发布，已发布的版本只读。某座窑装一批料开跑时，这批料就绑定到当时的有效基准版本。

运行过程由读数记录推动。每条记录带记录编号、窑号、时刻，内容是干湿球温度，或者样板称重。服务端要由干湿球温度推出相对湿度，再推出木材平衡含水率，吸湿模型用业界通行的一种并写明出处，参考值：20°C、相对湿度 65% 时平衡含水率约 12.0%，60°C、80% 时约 13.6%，允许 ±0.3 个百分点。样板含水率按绝干质量折算：初始称重 5000 克、初始含水率 60% 的样板，之后称得 4062.5 克时含水率为 30%。两次称重之间的含水率怎么估计由你决定：保持上次值最简单但阶段切换会滞后，按当前温湿度条件推一条干燥曲线更及时但依赖模型参数，请选定做法并在文档里讲清理由、误差来源和它会让阶段切换提前还是推后。估计值越过当前阶段的进入条件时，窑进入下一阶段，切换时刻要记下来。

有几件事要保证：同一个记录编号重复上报只算一次；记录晚到、时刻早于已处理的记录时，最终的阶段切换时刻要和按时刻顺序上报得到的一模一样；对一批料从头回放它的全部记录，得到的阶段序列和切换时刻与在线推进的结果逐项相同；服务重启后状态从持久化的记录恢复，不丢不重。批料运行中如果它所用的树种或厚度层发布了新版本，这批料是一直用旧版本跑完，还是在下一个阶段边界切到新版本，要给出明确规则，页面上能看到每批料实际用的是哪个版本、从哪一阶段开始换的。两个工艺员同时修改同一张表的草稿，后保存的一方要收到冲突提示，不能静默覆盖。

页面需要：三层基准的表格编辑与合并预览（标出每格来自哪一层）；版本发布与版本间差异对比；每座窑的温湿度曲线、含水率曲线和阶段时间轴；手工补录读数。页面只负责编辑和展示，计算都在后端完成。

以下输入要拒收并指明字段：相对湿度推算结果不在 0 到 100 之间（湿球高于干球）、阶段进入条件的含水率不是逐行递减、温度超出 0 到 120°C、称重为负或样板初始含水率不在 0 到 200% 之间、引用不存在的窑或树种。

测试要覆盖上面的平衡含水率与样板折算参考值、合并结果与保存顺序无关、乱序与顺序上报一致、重复记录幂等、全量回放与在线推进一致、重启恢复、版本切换规则、草稿并发冲突。

后端用 Node.js 20 + TypeScript + Fastify，数据放 PostgreSQL 16；前端 Vue 3 + Vite。基准合并、吸湿模型、含水率估计、阶段推进、记录流、接口路由、前端各视图分别成模块，别把核心逻辑写进一个大文件。后端测试用 Vitest。交付 Dockerfile（基于 node:20-alpine，构建阶段打出前端静态文件由后端托管）和 compose 文件，数据库用 postgres:16-alpine。
